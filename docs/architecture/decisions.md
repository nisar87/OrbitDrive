# Decisions and deviations from the build pack

| ID | Decision | Why | Revisit |
|---|---|---|---|
| ADR-1 | Agent control channel is a plain WebSocket carrying the versioned typed envelope, **not SignalR** (the plan's D3 suggestion) | The envelope/correlation/deadline protocol is defined in the canonical schema either way; SignalR's client is an extra dependency in the per-user agent, and this build environment cannot restore NuGet packages to verify it locally. Transport sits behind `AgentConnection`/`ControlClient` | **Kept** after D3/W3: leases, heartbeats and the fault-injection suite run on it (ADR-12). Still contained to two classes if the owner prefers SignalR |
| ADR-2 | Agent byte uplink is `POST /v1/agent-streams/{id}` with a streamed body rather than a binary WebSocket | HTTP request-body streaming gives end-to-end backpressure with no framing code; one-use bearer token per stream | D5 if resumable uplinks need it |
| ADR-3 | Gateway and agent production code use only the .NET shared framework (no third-party packages) so far; DPAPI and Win32 file APIs via P/Invoke | Smaller attack surface; locally verifiable | W1 adds the official Firebase Admin SDK as planned |
| ADR-4 | Durable metadata is a file-backed `Store` (atomic JSON snapshot under `OrbitDrive:DataDirectory`; memory-only when unset) | Firestore needs service credentials. Single relay instance only; pairings and download capabilities are never persisted (fail closed) | When Firestore credentials exist or a second relay instance is needed |
| ADR-5 | Identity is a development HMAC verifier behind `IIdentityVerifier`; Production refuses to start | Firebase project/config not available; W1 | W1 |
| ADR-6 | 64-bit integers are decimal strings on the wire, rejected if sent as JSON numbers | JavaScript cannot represent sizes above 2^53 exactly | — |
| ADR-7 | Multi-range requests are answered with the full representation (200) | Permitted by RFC 9110; avoids multipart complexity and abuse | W5 |
| ADR-8 | Hard-linked files are refused on Windows | Reparse checks alone do not establish unique origin | D4 |
| ADR-9 | Workflows have no path filters yet | Avoids required checks that never start; revisit when CI minutes matter | W11 |
| ADR-10 | `main` is the default branch and only ever fast-forwards to commits with all seven workflows green; work lands on `feature/orbitdrive-foundation` first | Owner authorised `main` on 2026-11-17 on condition of proper testing | — |
| ADR-11 | Firebase ID tokens are verified in the gateway with framework cryptography following Firebase's documented third-party-verification rules, **not the Admin SDK** (plan W1 suggestion) | Keeps the gateway free of third-party packages and fully testable (real RS256 tokens, 22 cases). Cost: no `checkRevoked` yet — account-level token revocation is not enforced until service credentials exist; OrbitDrive device grants are still revoked on every request | W3, when service credentials arrive. **Owner decision welcome** |
| ADR-12 | Liveness is an application-level lease: the gateway tells an agent its heartbeat interval and lease in the welcome (10 s / 30 s by default); the agent sends `heartbeat` requests, the gateway answers each, and either side drops the connection after a full lease of silence. Applies only to agents announcing the `heartbeat` capability | WebSocket ping/pong is invisible to application code and does not prove the agent's message loop is alive; a frozen PC or half-open connection must not look online. Older agents keep working unleased | Tighten once all agents heartbeat (make it mandatory with a protocol bump) |
| ADR-13 | In-site QR scanning uses the browser's `BarcodeDetector` when it supports QR codes and otherwise the bundled `jsqr` decoder (Apache-2.0, loaded on demand). Scanned text is accepted only if it is this site's own `/pair#…` link or the bare manual code; the scanned URL is never opened | Works on browsers without a native detector; keeps frames on the device; a QR cannot redirect the user to another origin | Replace `jsqr` if it becomes unmaintained |
| ADR-14 | Thumbnails are produced by a separate helper process (`OrbitDrive.ThumbnailHelper`, SkiaSharp 4.150.1) that the agent starts per image: bytes in on stdin, WebP out on stdout, 15 s timeout, 512 KiB output cap, process tree killed on timeout; on Windows it runs in a job object (768 MiB, one process, kill-on-close, fail-closed). The agent itself stays framework-only (ADR-3) and never references the decoder. | Image decoders are the most attacked code in the product; keeping one out of the agent process contains a decoder bug to a disposable, memory-limited process with no handles. Header size is checked in managed code first (`ImageProbe`: 64 MP, 30 000 px) so decompression bombs never reach the decoder | D8 (vector/RAW formats, a lower-privilege token for the helper) |
| ADR-15 | Previews are ordinary read sessions flagged `preview`, served inline only for a closed content allow-list judged from the **bytes** (not the name), with `Content-Security-Policy: default-src 'none'; sandbox`, `nosniff`, no-store. HTML, SVG, XML and executables are never inline. Preview sessions never appear in Transfers and have their own caps. Thumbnails use a derived token that re-validates the source before every read and cached files are named by hash | Opening a file to look at it must not become a way to run it. Text is shown by the web app as text only | Isolate the PDF renderer in a sandboxed iframe on a separate origin (open item) |
| ADR-16 | Folder and multi-select ZIPs are **staged on the PC, never streamed**. A job walks the selection through the same access boundary as browsing, writes a seekable ZIP (own CRC32, deflate/stored, headers patched after copy, ZIP64 per entry ≥ 0xF0000000 and for ≥ 0xFFFF entries) to the agent's private staging area, then serves it as an ordinary resumable read (variant "archive"). Limits: 20 GiB source, 24 GiB staged, 100 000 files, 200 selected items, depth 64, 3 active jobs, 6 h TTL, 512 MiB free-space reserve. Anything skipped (links, hidden/system, unsafe names, unreadable, changed during build) is listed in the UI **and** in `_OrbitDrive_omitted.txt` inside the ZIP, and the archive is labelled incomplete; strict mode fails instead. Reason for staging: a streamed ZIP cannot be resumed or verified, and a source that changes mid-stream would produce a silently wrong archive. Cost: temporary disk on the PC. |
| ADR-17 | Filename search is **live, not indexed**: a bounded BFS over the shared folders through `EnumerateChildren` (the browsing access path), so revoked or unshared folders can never appear and nothing about file names is stored anywhere. Limits: 100 hits, 20 000 folders, 300 000 entries, depth 48, 8 s; cancellable; every incomplete answer carries a reason (`limit`, `time`, `scan_limit`, `unreadable`, `cancelled`, `unavailable`). Across PCs the web asks each online PC separately; an offline PC is shown as offline and an incomplete answer is never presented as "no matches". |
| ADR-18 | One browser device identity spans all PCs the account pairs it with (the claim reuses the existing device). Each PC still holds its own grant, so unpairing on one PC is PC-scoped, while revoking the device is global. Favorites/recents are stored only in the browser, keyed by PC, shared folder, kind and path (entry ids are re-issued per listing) and are re-validated with `entry-checks` before use; a stale item shows "Unavailable" and can be removed. |
| ADR-19 | Uploads are **owner-enabled per shared folder and never overwrite**. The owner turns uploads on for a SharedRoot (CLI `roots uploads`, local IPC, WPF) with a per-file limit and a quota; every root is read-only otherwise. The browser names a root, an optional folder entry id and a file name — never a path. Only collision policies `reject` (default) and `rename` ("name (2).ext") exist; there is no overwrite or delete. Names and extensions that auto-run or hide (`desktop.ini`, `.lnk`, `.url`, `.scf`, …), bidi/control characters and paths over 259 characters are refused. Windows files get Mark-of-the-Web (`Zone.Identifier`). Nothing is opened, run or unpacked and no antivirus claim is made | An upload is the first write path; the smallest safe grant is "this folder, within these limits, add-only" | D9/W9 |
| ADR-20 | Upload data is **chunked, strictly sequenced and checksummed**: server-chosen 2 MiB pieces (hard max 8 MiB), each with a client SHA-256; a piece is held in memory once, verified, written at its offset into a private `.orbitdrive-partial` folder, flushed, and only then does the committed offset advance. Duplicate/out-of-order pieces change nothing and return the PC's real offset; a wrong checksum stores nothing. Finish (idempotent) renames atomically with `MoveNoReplace` (Windows `File.Move(overwrite:false)`; Linux `link()`+delete) into a folder pinned to the root and disk. The piece travels browser → gateway `PUT` → PC via a one-use downlink the agent dials out (`GET /v1/agent-downlinks/{id}`), so the gateway buffers nothing. Sessions live in agent memory only: **an agent restart ends them** (partials are deleted at start) and the browser must start again | Bounded memory on all three parts; the PC's committed count is the only truth; crash cannot leave a half file under a real name | D9/W9 |
| ADR-21 | **Operators are named by deployment configuration, never by sign-up.** `OrbitDrive:OperatorUids` lists verified user ids; every `/v1/admin/*` call re-checks the list and requires a sign-in at most 15 minutes old (`auth_time`, not token refresh). The admin area is a lazy-loaded chunk offered only to accounts the service reports as operators, but the server, not the hidden route, is the boundary. Admin can see aggregate counters, account ids with counts, and an audit trail; it can suspend/unsuspend, sign out all browsers of an account, restore a day's relay allowance and set the oldest PC version. There is no endpoint that lists files, folders, paths or acts as a user. Operator accounts cannot be suspended through the API. This is an application permission boundary and does not claim the operator cannot see TLS-terminated traffic | A hidden route is not security; first-registrant-is-admin is a takeover; operators must be accountable | D10/W10 |
| ADR-22 | **Account deletion removes the service's links, never PC files.** Deleting (recent sign-in + typed phrase) revokes every browser, releases every PC (the PC keeps its own folders and settings), erases preferences, day counters and the stored email and display name (R65), and ends live transfers. A suspension survives deletion so deleting cannot undo a block. The audit log keeps the account id and time of the deletion (and, since R65, the email the account had, so the entry stays readable) until the operator deletes the data directory; backups of the data directory are the operator's to expire, so deletion is not promised to be instant everywhere | Owners need to leave; the relay must not hold data it has no use for; abuse blocks must stick | D10/W10 |
| ADR-23 | **Updates are verified before they are believed.** An ECDSA P-256 signature by a key built into the app over the exact manifest bytes, then channel, protocol range, freshness (expiry, no future dating, at most 90 days), strictly newer than running and than the newest version ever accepted (rollback/replay), a file for this architecture, https only from a listed host with no userinfo/port/query, a safe file name with an installer extension, signed size and SHA-256. The file is hashed while it arrives, renamed into place only if exact, hashed again immediately before the installer is launched, after running work was drained. A journal makes an interrupted apply visible at the next start. No code path takes an update URL from anywhere but a verified manifest. **Not done:** installer packaging (MSIX), production signing key and the Windows 11 install/upgrade/uninstall evidence, which need the owner's signing identity and machine | R44 is a security control; the engine can be proven cross-platform even though packaging cannot | D10 |
| ADR-24 | **Operators see an account's email, and nobody else does (R65, owner decision 2026-11-26).** The gateway takes `email` (and `name`) from the verified sign-in token on each authenticated request and stores them in the billing record (`account/<uid>`, write-behind; memory, file and Firestore stores alike). Only `/v1/admin/*` returns them. Audit entries carry the operator's and target's email as at the time; account deletion erases the billing copy. Never in a URL or a log. Customer endpoints, including the organisation panel, gain no email | Operators could not tell whom a suspend, sign-out or payment check affected when accounts were opaque ids | R65 |
